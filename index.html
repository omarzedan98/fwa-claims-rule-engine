FWA Claims Rule Engine

A rule engine that screens health-insurance claim exports for fraud, waste and abuse. It runs 32 rules over every claim and service line, writes a reason next to each finding, and adapts to whatever layout the claims export arrives in.

This example is built for the Saudi market, using NPHIES service codes (SBS), ICD-10, the SFDA drug register and the NPHIES GTIN list. The rules are not tied to them: the code lists can be swapped for other standards, such as CPT, HCPCS, ICD-10-CM or NDC drug codes.

The problem

Medical claim audit is mostly manual. Reviewers sample claims and look for the same patterns again and again: the same service billed twice, a diagnosis that cannot apply to the patient's age or sex, one claim copied across many members, drugs that duplicate each other, a visit billed after the policy expired. Each check is simple; doing all of them on every line of a large export is not.

This project turns those checks into explicit, documented rules that run on the whole file in one pass, against the coding standards providers bill with: NPHIES service codes (SBS), ICD-10 diagnoses, the SFDA drug register and the NPHIES GTIN list.

How it works

  1. Map the export

    A column converter matches the file's headers to a 60-column claims template. Headers are mapped once in the app and remembered; older export spellings are recognised automatically. Service-type wording (CONS, MEDS, LBRD…) maps to seven types.

  2. Load the standards

    SBS, ICD-10, the SFDA drug list and the NPHIES GTIN list sit next to the app and are reused every run. Uploading a newer version replaces the stored copy.

  3. Run the rules

    Unpaid lines are set aside, then the claim-level rules and the service-line rules run in a fixed order, so a rule that depends on another always sees its result.

  4. Deliver the findings

    An Excel workbook with a reason written next to every flagged line, in the layout the reviewer chose before the run, ready to hand to the audit team.

  5. Track it on the dashboard

    Alongside the workbook, an interactive dashboard turns the findings into money and trends: billed against rejected amount, rejections by rule and provider, and how both move month by month.

Why the dashboard matters

A findings list says what is wrong; the dashboard says where to act first. It shows how much of what was paid the rules would reject, which providers and which rules drive that amount, and whether a pattern is growing or fading over time. That turns screening into something a manager can prioritise and report on: rejection rate, savings by rule, and providers to audit or educate.

  • Headline cards — total paid and rejected amount, with the rejection rate. A line that breaks several rules is counted once, so the rejected amount is never inflated.
  • Billed and rejected over time — one line per provider, by month, quarter or year, to spot a provider whose billing or rejections jump.
  • Rejected amount by rule — which rules carry the money, at claim or service level; any rule can be hidden so the others rescale into view.
  • Provider behaviour — each provider's share of unlisted codes against its limit, and the services a provider or physician attaches to most of their claims.
  • Filters — provider, period (year, quarter, month or a custom range) and service type, applied across the page.

Claim level5 rules

  • C1Duplicate ClaimTwo or more claims for the same patient on the same day billing exactly the same set of services.
  • C2Member Treated at Multiple Providers, Same DayA patient with paid consultation lines at two or more different providers on one day.
  • C3Cloned ClaimsThe same provider, anywhere in the file, billing an identical set of services, principal diagnoses and chief complaint for different patients.
  • C4-1Physician Daily Capacity Breach (doubtful)A physician seeing more than 40 different patients in consultation on one day.
  • C4-2Physician Daily Capacity Breach (confirmed)A physician seeing 60 or more different patients in consultation on one day.

Duplication and frequency9 rules

  • S1Duplicate ServiceThe same service billed more than once for the same patient on the same day.
  • S2Repeat Consultation Within 14 DaysThe same patient seen again by the same physician 1 to 14 days after the previous visit.
  • S3Service Frequency BreachA service repeated sooner than the frequency SBS sets for its NPHIES code, counted across providers.
  • S4Excessive RadiologyMore than 3 radiology studies for the same patient in a rolling 14 days.
  • S5Exceeds Maximum Daily LimitA line billed with a quantity greater than the daily limit SBS sets for its NPHIES code.
  • S6Unreasonable QuantityA drug line billed with a quantity above 5.
  • S7Duplicated Service Within 7 DaysThe same service for the same patient at the same provider repeated 1 to 7 days later.
  • S11Excessive Consultation FrequencyA patient with more than 3 consultation-only claims inside a rolling 30 days.
  • S22Excessive Member VisitsA patient with more than 5 visit days inside a rolling 30 days, counted across every provider and service type.

Coding validity7 rules

  • S8Diagnosis Outside Age RangeA diagnosis code billed for a patient whose age at the service date is outside the range ICD-10 allows.
  • S9Diagnosis Gender MismatchA diagnosis code ICD-10 strictly restricts to one sex, billed for a patient of the other.
  • S12Invalid ICD-10 CodeA diagnosis code marked valid = 0 in ICD-10, or absent from the reference altogether.
  • S13Inactive ICD-10 CodeA diagnosis code ICD-10 had withdrawn by the service date and not reactivated.
  • S14Not Valid Principal DiagnosisA primary diagnosis that ICD-10 allows only as an additional diagnosis.
  • S15Service / Gender MismatchA service SBS restricts to one sex, billed for a patient of the other.
  • S16Service / Age MismatchA service billed for a patient outside the age range SBS allows it for.

Pharmacy3 rules

  • S17-1Therapeutic Duplication, Same Active IngredientTwo different drugs given to one patient on one day that share the ATC code to 7 characters (same active ingredient).
  • S17-2Therapeutic Duplication, Same Chemical SubgroupTwo different drugs given to one patient on one day that share the ATC code to 5 characters (same chemical subgroup).
  • S17-3Therapeutic Duplication, Same Pharmacological SubgroupTwo different drugs given to one patient on one day that share the ATC code to 4 characters (same pharmacological subgroup).

Provider and physician behaviour4 rules

  • S18-1More Than 5% Unlisted SBS CodesEvery unlisted service from a provider whose unlisted share of non-drug lines is 5% or more.
  • S18-2More Than 3% Unlisted DrugsEvery unlisted drug from a provider whose unlisted share of drug lines is 3% or more.
  • S19-1Service Too Frequent Use, Provider LevelA service or drug that appears on more than 70% of a provider's claims, consultation excluded.
  • S19-2Service Too Frequent Use, Physician LevelA service or drug that appears on more than 70% of a physician's claims, consultation excluded.

Documentation and coverage4 rules

  • S10Isolated Consultation VisitA claim billing nothing but consultation, with no test, medicine or procedure that followed.
  • S20-1Phantom BillingA paid line on a claim whose chief complaint says the visit was cancelled or the patient not seen.
  • S20-2Missed Chief ComplaintA paid line on a claim with no chief complaint, or one holding no real word.
  • S21Service Outside CoverageA service dated before the policy start date or after the policy end date.

Built to fit any claims data

Any layout

  • A 60-column template covers member, policy, claim, diagnosis, service, amount and rejection fields.
  • A mapping screen ties each template field to the file's own header; the mapping is saved and reused.
  • Fields a file does not have are created blank, so a partial export still runs; rules that need a missing field say so instead of failing.
  • Results are written back under the file's own header names.

Any size

  • No fixed line limit: rules work on whole columns at once rather than row by row.
  • A results sheet that passes Excel's 1,048,575-row limit continues on a second sheet automatically.
  • A fast copy of the upload (Parquet) makes repeat runs on the same file load in seconds.
  • Reference tables can be swapped for newer releases without touching the rules.

How the rules were set and proven

Thresholds from the data

Limits were measured before they were chosen. For example, the excessive-visits rule counts each patient's visit days in a rolling 30 days; visit counts are heavily skewed, so the limit came from Tukey's outlier fences on that distribution rather than a guess.

Tested at the boundary

Every rule has tests built at its exact limit: at the threshold it stays quiet, one past it fires, the wrong service type never fires, and a missing reference leaves it silent with a warning instead of an error.

Checked against a recount

On a full file, each new or changed rule is recounted by a separately written method and compared line by line, and every other rule is confirmed unchanged before the change is kept.

Documented for review

A rules reference workbook, a flowchart per rule, and a shared review page where stakeholders comment on a rule after reviewing its results.

I designed every rule, chose and tested the thresholds against real-world claim patterns, specified how findings are reported, and validated the results. The engine is implemented in Python (pandas) with a Streamlit app and dashboard, built with AI-assisted development.
